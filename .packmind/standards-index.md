# Packmind Standards Index

This standards index contains all available coding standards that can be used by AI agents (like Cursor, Claude Code, GitHub Copilot) to find and apply proven practices in coding tasks.

## Available Standards

- [Application Service Structure](./standards/application-service-structure.md) : Enforce Python application service structure under `src/application/services/*_service.py` with constructor-injected port interfaces (`I*.py`/`i_*.py`), no direct IO or `infrastructure/` imports, clear command/query separation, and post-change domain event publication via `IDomainEventBus` to preserve layering, testability, and maintainable orchestration.
- [Background Job Three-Layer Pattern](./standards/delayed-job-three-layer-pattern.md) : Enforce a three-layer background job architecture—domain contracts (`domain/jobs` with `{JobName}Input/{JobName}Output` interfaces or Python `@dataclass` plus `I{JobName}Job` ABC), application implementations (`application/jobs` extending `AbstractAIDelayedJob<Input, Output>` or implementing `I{JobName}Job`), and infrastructure wiring (`infra/infrastructure/jobs` via `IJobFactory`/`IJobQueue` or Celery/asyncio tasks)—to isolate queue technology from domain intent and keep job logic independently testable.
- [Background Job Three-Layer Pattern](./standards/background-job-three-layer-pattern.md) : Enforce a three-layer background job structure with `@dataclass` input/output and an ABC `I{JobName}Job.execute(...)` contract in `domain/jobs/{job_name}.py`, a dependency-injected implementation in `application/jobs/{job_name}_job.py`, and Celery/asyncio task wiring in `infrastructure/jobs/{job_name}_task.py` to isolate queue infrastructure from domain intent and keep job logic independently testable.
- [Domain Error Structure](./standards/domain-error-structure.md) : Standardize domain error classes in `packages/{domain}/src/domain/errors/{ErrorName}.ts` using `{Entity}{Condition}Error` naming, direct `Error` extension with `super(humanReadableMessage)` and `this.name` set after `super()`, typed entity ID parameters, and no `Object.setPrototypeOf` to enable reliable identification and handling in catch clauses.
- [Domain Events for Cross-Layer Communication](./standards/domain-events-for-cross-layer-communication.md) : Standardize cross-layer state-change communication in the AEFI system by modeling each transition as a `DomainEvent` dataclass in `src/domain/events/`, publishing via `IDomainEventBus` with the lowercase class name as the topic, subscribing in application service `__init__`, and forwarding only to interface `present_*` methods to keep services and presenters decoupled and avoid leaking infrastructure events.
- [Persistence Model Mixin Composition](./standards/typeorm-entity-schema-composition.md) : Standardize SQLAlchemy persistence models by composing `TimestampMixin` and `SoftDeleteMixin` (kept in `infrastructure/persistence/mixins.py`) and defining TypeScript schemas in `infra/schemas/{EntityName}Schema.ts` as `EntitySchema<WithTimestamps<Entity>>` or `EntitySchema<WithSoftDelete<WithTimestamps<Entity>>>` using `...uuidSchema`, `...timestampsSchemas`, and `...softDeleteSchemas` from `@packmind/node-utils`, snake_case column `name:` mappings, and entity imports from `@packmind/types` to ensure consistent columns and types without repetition.
- [Persistence Model Mixin Composition](./standards/persistence-model-mixin-composition.md) : Standardize SQLAlchemy entity models by composing TimestampMixin and SoftDeleteMixin from infrastructure/persistence/mixins.py and organizing models as infrastructure/persistence/{entity_name}_model.py exported as {EntityName}Model with domain-only imports to ensure consistent columns, clean layering, and reduced duplication.
- [Port Interface Naming and Placement](./standards/port-interface-naming-and-placement.md) : Enforce Hexagonal Architecture port interface naming and placement for Python `ABC` contracts under `src/application/` and `src/domain/` (use `i_*.py` beside consuming services, separate input/output ports, `@abstractmethod`-only methods with Responsibility/Rationale/Design docstrings, and no implementation logic) to keep service–adapter boundaries explicit and maintainable.
- [Presenter Responsibility Boundary](./standards/presenter-responsibility-boundary.md) : Enforce a Presenter Responsibility Boundary for Python Qt presenters in `src/interface/presenters/*_presenter.py` by inheriting from `QObject` and the service output port, emitting Qt signals in output-port methods, handling `@Slot` user actions by forwarding to application services, registering via `service.set_output_port(self)` in `__init__`, and avoiding domain imports and business computations (e.g., ETA) to keep UI glue thin and business logic testable and maintainable.
- [Repository Aggregator Pattern](./standards/repository-aggregator-pattern.md) : Standardize grouping domain entity repositories behind an `I{Domain}Repositories` interface implemented by `{Domain}Repositories` using a TypeORM `DataSource` and `dataSource.getRepository({EntitySchema})` getters to simplify dependency injection and decouple use cases from repository implementations.
- [SolidAI — Aggregate Domain : Racine, Entités et Value Objects](./standards/solidai-aggregate-domain-racine-entites-et-value-objects.md) : Standardize each SolidAI domain module as a single-aggregate structure with one dataclass aggregate root at the module root (Trio Atomique: intention.md + implementation + _tests/), entities in entities/, immutable identityless value objects in value_objects/, and immutable domain events in events/ (each with its own Trio Atomique) to make aggregate boundaries, invariants, and responsibilities immediately navigable and unambiguous.
- [SolidAI — Aggregate Domain : Racine, Entités, Value Objects et Events](./standards/solidai-aggregate-domain-racine-entites-value-objects-et-events.md) : Standardiser l’anatomie des modules domain SolidAI en structurant chaque agrégat avec un unique aggregate root Python dataclass à la racine (Trio Atomique <module>_intention.md + implémentation + _tests/), des entités/value objects/events isolés dans entities/, value_objects/ et events/ avec leur propre Trio Atomique, et des interfaces dans repositories/ sans imports hors domain/ ni logique d’infrastructure afin de préserver les invariants, éviter les collisions de noms et améliorer la maintenabilité.
- [SolidAI — Architecture Fractale Trio Atomique : Intention, Code, Tests Co-localisés](./standards/solidai-architecture-fractale-trio-atomique-intention-code-tests-co-localises.md) : Enforce the SolidAI “Trio Atomique” fractal module layout—<module>_intention.md (Rationale/Responsibility/Design), <module>.py, and co-localized _tests/<module>_test.py at distance 1 (never .test.py)—to standardize DDD architecture, preserve Python import resolution, and make intent, implementation, and validation auditable while minimizing architectural debt.
- [SolidAI — Graph of Intentions (Promise↔DDD) Modeling](./standards/solidai-graph-of-intentions-promiseddd-modeling.md) : Appliquer une taxonomie stable et traçable (sources, tags, mappings) pour faire émerger des fonctionnalités atomiques et guider leur projection en DDD.
- [SolidAI — Graphe de Pensée : Ossature DDD-Crew et Règles de Traversal [EXPÉRIMENTAL]](./standards/solidai-graphe-de-pensee-ossature-ddd-crew-et-regles-de-traversal-experimental.md) : Structurer les nœuds du graphe de pensée en trois couches de stabilité calquées sur le DDD Starter Modelling Process, et guider l'agent dans sa traversée du stable vers le volatile.
- [SolidAI — Navigation Agents IA : Placement Déterministe Fake, Real, Interface, Atome](./standards/solidai-navigation-agents-ia-placement-deterministe-fake-real-interface-atome.md) : Appliquer un placement déterministe des fichiers (Interfaces/Ports → domain/repositories/ ou application/<service>/ports/, Real → infrastructure/<adapter>/<adapter>.py, Fake → infrastructure/<adapter>/fake/fake_<adapter>.py) en synchronisant le Meta-Domain (Markdown/Gherkin) et src/ via intention.md et en organisant les tests par couche (domain/application/infrastructure) pour accélérer la navigation, réduire l’ambiguïté et maintenir l’architecture cohérente.
- [SolidAI — Nomenclature : snake_case, Préfixes I/fake_, Dossier _tests/, Suffixe _test.py](./standards/solidai-nomenclature-snakecase-prefixes-ifake-dossier-tests-suffixe-testpy.md) : Standardize SolidAI file, folder, and class naming with snake_case, _tests/ for test directories, _test.py (never .test.py) for Python tests, I-prefixed Domain interfaces, fake_-prefixed Fakes, and an invariant intention.md to enable deterministic O(1) navigation and avoid Python import-resolution issues.
- [SolidAI — Règles d'Import DDD : Isolation Domain, Application, Infrastructure](./standards/solidai-regles-dimport-ddd-isolation-domain-application-infrastructure.md) : Enforce strict DDD import rules where domain/ never imports infrastructure/, application/ imports only Domain and uses infrastructure/<adapter>/fake/ in tests (never the Real adapter), and Infrastructure implements Domain interfaces with Real and Fake co-located to preserve layer isolation, independent testability, and parallel development.
- [SolidAI — Services Applicatifs : Structure, Interfaces et Ports Infrastructure](./standards/solidai-services-applicatifs-structure-interfaces-et-ports-infrastructure-1.md) : Définit la structure obligatoire d'un service applicatif : interface API inbound (i_api_), ports outbound dans application/X_service/ports/ (i_), DTOs, et co-localisation en trio atomique.
- [SolidAI — Test Doubles DDD : Fake In-Memory vs Mock, Placement Infrastructure](./standards/solidai-test-doubles-ddd-fake-in-memory-vs-mock-placement-infrastructure.md) : Standardize DDD test doubles by colocating functional in-memory Fakes beside their Real in infrastructure/<adapter>/fake/ (with intention.md, implementation, and _tests/) and preferring them over interaction-based Mocks for application use cases to validate domain contracts, ensure test propagation to real infrastructure, and avoid unnecessary doubles for pure computational adapters.
- [Test Mock Placement and DTO Construction](./standards/test-mock-placement-and-dto-construction.md) : Standardize Python test mock adapter placement in `src/infrastructure/mocks/` (using `adapter_mock_` file prefixes), event bus usage via `InMemoryEventBus`, and reusable DTO factories `make_<dto_name>(**overrides)` (with concise setup and `DiagramFriendlyTest` for service flows) to reduce duplication and keep tests stable and maintainable.
- [Typed Entity ID Pattern](./standards/branded-entity-id-pattern.md) : Enforce branded typed entity ID aliases using `Branded<'{EntityName}Id'>` and `brandedIdFactory` from `../brandedTypes`, created and imported from canonical `packages/types/src/{domain}/{EntityName}Id.ts` and cast from raw strings only at domain boundaries via the factory (never `as {EntityName}Id` or bare `string`/`number`), to prevent cross-entity ID mixups at type-check time and clarify domain boundaries in signatures.
- [Typed Entity ID Pattern](./standards/typed-entity-id-pattern.md) : Enforce typed domain entity IDs in Python using NewType-defined `{EntityName}Id` aliases stored in `domain/{entity_name}_id.py` and used instead of bare `str`, casting only at domain boundaries, to prevent ID type mixups and make domain boundaries explicit in signatures.
